### 1. `searchsorted` кастует весь массив ключей на каждом вызове — блокер

```python
mid = int(np.searchsorted(keys, T, side='left'))   # T — Python int
```

`keys` — uint64, `T` — Python int. NumPy приводит uint64 + int64 к **float64**
(`np.result_type(np.uint64, np.asarray(5))` → `float64`), то есть копирует и
конвертирует **весь массив ключей** на каждом вызове. Двоичный поиск за O(log n)
превращается во временный массив на весь датасет.

Замерено на 6 млн записей: **22.3 мс** против **19.6 мкс** с `np.uint64(T)` —
разница в **1138×**. `build` делает один `searchsorted` на каждый внутренний узел.
На целевом enwik8 (800 млн записей, миллионы внутренних узлов) это временный
float64-массив на 6.4 ГБ **на каждый узел** — процесс не финиширует никогда.

Это ровно то, ради чего писался весь пайплайн внешней сортировки.

**Исправление:** `np.searchsorted(keys, np.uint64(T), side='left')`.

### 2. То же приведение ломает разбиение при `--depth > 53`

float64 теряет точность выше 2⁵³. Проверено: для
`keys = [2⁶⁰, 2⁶⁰+1, 2⁶⁰+2, 2⁶⁰+3]` (uint64) и `T = 2⁶⁰+2`

- `np.searchsorted(keys, T)` → **0** (Python int),
- `np.searchsorted(keys, np.uint64(T))` → **2** (верно).

`--depth` задаётся пользователем, `DEFAULT_DEPTH = 48` лежит под порогом только
по случайности. `--depth 56` построит структурно неверное дерево — неверные
`n0`/`n1`, неверная оболочка, без единого сообщения об ошибке. Проверки
эквивалентности шли на D ≤ 16 и такое не ловят.

Чинится тем же `np.uint64(T)`.

### 3. Куча без предела — OOM, уже исправленный в Rust

`weakest_link_frontier_sa` делает push на каждого предка при каждом отщипывании
и ничего не ограничивает. `src/comparator.rs:182-189` описывает ровно этот отказ:

> записи устаревают при каждом пересчёте предков (O(узлы×глубина) push'ей
> суммарно — это и был OOM 20 ГБ)

и добавляет `heap_cap` с периодической перестройкой из живых кандидатов.
В Python-пути такого нет. При ожидаемых 2–5 млн контрактированных узлов × 48
глубины это ~10⁸ кортежей `(float, int, int)` по ~150 Б — десятки гигабайт.
`sa_prod.frontier_sa` (строка 174) импортирует эту функцию напрямую, то есть
продакшн-запуск идёт прямо в тот OOM, от которого Rust-версию уже вылечили.

**Исправление:** перенести cap + перестройку из `comparator.rs`.

### 4. Верхний уровень слияния грузит весь датасет в RAM

При `MERGE_WAY = 4` последний раунд собирает 4 файла по N/4 записей — то есть
весь датасет. Для enwik8 (800 млн × 13 Б) это 10.4 ГБ через `np.load`, плюс
копия на `np.concatenate` ещё 10.4 ГБ, плюс рабочая память сортировки: **более
20 ГБ пика**. Докстринг (строка 8) обещает «пик ~2 ГБ».

`stage5b-comparator-status.md:29-33` мотивирует существование этого файла именно
тем, что 6.4 + 6.4 ГБ не влезают — реализация возвращает то самое ограничение,
от которого уходила. Нужно потоковое k-путное слияние
(`heapq.merge` / поблочное слияние фронтов), тогда пик — один блок на вход.

### 5. Узлы переупакованы в Python-словари

Строки 164-168 собирают по словарю на узел плюс словарь `first_occ`. Замер

| | 2 млн узлов | 5 млн узлов |

На машине из `stage5b-comparator-status.md:32` (~0.5 ГБ свободно) это OOM.
Причём докстринг строки 99 описывает **правильный** дизайн — «nodes — списки

### 7. `pos` как uint32 заворачивается на входах > 512 МиБ

```python
rec['pos'] = np.arange(cs, cs + L, dtype=np.uint32)
```

Проверено: `np.arange(2**32-4, 2**32+4, dtype=np.uint32)` возвращает
`[…4294967295, 0, 1, 2, 3]` — без ошибки и без предупреждения. enwik9 (1 ГБ) —
это 8·10⁹ бит, почти вдвое больше диапазона uint32.

Завёрнутые позиции портят `first_occ` — ключ тай-брейка, на котором держится вся
конструкция («heap-ключ (α, first_occ, dep) — последовательность отщипываний
ИДЕНТИЧНА explicit»), так что оболочка молча разойдётся с явным деревом.
Нужен uint64 либо явный отказ на входах > 512 МиБ.

### 8. Счётчики `u32` в `comparator.rs` переполняются на входах > 512 МиБ

`n: [u32; 2]` — у корня `n[0] + n[1]` равно общему числу битов. 1 ГБ (enwik9,
на который ссылаются `research/` и `notes/bibliography.md`) даёт 8·10⁹ >
`u32::MAX` = 4.29·10⁹. Сборка идёт с `rustc -O` (заголовок, строка 25), а там
переполнение **молча заворачивается**, а не паникует: `cost_leaf` посчитает
энтропию от завёрнутых счётчиков, и bpc окажется неверным без ошибки. Первыми
страдают узлы у корня. Либо `u64`, либо явная проверка `data.len()` на старте
(`--limit` есть, но по умолчанию `usize::MAX`).

### 9. Промежуточные файлы слияния не удаляются

`merge_all` пишет каждый уровень в новые файлы и делает `files = nxt`, не удаляя
только что поглощённые входы (`del parts, merged` на строке 88 отпускает только
ссылки в памяти; `os.remove` в файле нет вообще). Для enwik8 при `CHUNK = 8M` это
100 чанков и ~4 уровня слияния, то есть пик по диску ≈ 5 × 10.4 ГБ = **50+ ГБ**
в `.sa_tmp` вместо двукратного, который нужен нормальной внешней сортировке.

### 10. `rmtree` не может удалить замапленные файлы, ошибка проглочена

Финальный `shutil.rmtree(tmpdir, ignore_errors=True)` выполняется, пока `mm`
(`np.load(mmap_mode='r')`) и `pref` (`np.memmap`) держат файлы открытыми.
Воспроизведено в ходе ревью: удаление даёт
`PermissionError: [WinError 32] The process cannot access the file because it is
being used by another process`. Среда — Windows 11.

Свидетельство на диске: `tools/.sa_tmp/` до сих пор хранит `rec_0000.npy` и
`rec_0000.npy.pref` от запуска 04.08 01:10. Без `--keep` пользователю ничего не
сообщается, а десятки гигабайт остаются; `.pref` (строка 110) вообще нигде не
закрывается и не удаляется. Нужно закрыть memmap'ы до `rmtree` и сообщать, что
удалить не удалось.

### 11. `rmtree` сносит пользовательский `--tmp` целиком

`tmpdir = args.tmp or …` (строка 190) принимает любой путь, а
`os.makedirs(tmpdir, exist_ok=True)` спокойно переиспользует существующий
каталог. `python sa_prod.py enwik8 --tmp D:\scratch` — естественный выбор, когда
по умолчанию не хватает 50 ГБ, — по завершении удалит **всё** в `D:\scratch`,
причём `ignore_errors=True` подавит любые жалобы. Стоит запоминать созданные
файлы и удалять только их (или отказываться от непустого каталога).

### 12. Пустой входной файл → `IndexError`

Воспроизведено: `generate(b'', 8, tmp)` возвращает `([], 0)`, затем
`merge_all([], …)` даёт `IndexError: list index out of range` — цикл
`while len(files) > 1` пропускается, и строка 92 разыменовывает пустой список.
Дальше по коду `nbits = len(data) * 8` = 0 и `full_cost / nbits` (строка 214)
дало бы `ZeroDivisionError`. Достаточно проверки непустого входа в `main()`.

### 13. Обратный словарь опирается на недокументированный инвариант

```python
fo_dep_to_u = {(first_occ[u], nodes[u]["dep"]): u for u in range(n)}
```

Инвариант сегодня выполняется — у позиции ровно один контекст длины d, поэтому
два узла глубины d не могут делить минимальную позицию, — но нигде не
зафиксирован и не проверяется. Если `first_occ` когда-нибудь станет
приблизительным (сэмплирование, переиспользование для контрактированных унарных
цепочек), отказ будет **молчаливым**: `u = fo_dep_to_u[(fo, dep)]` вернёт другой
живой узел, тот будет отщипнут и помечен мёртвым. `comparator_wl.py:74` этой
проблемы не имеет — там в кучу кладётся `(a, u)`. Достаточно класть
`(a, first_occ[u], dep, u)` и убрать словарь; заодно уйдёт O(n) памяти.

### 14. Мёртвый импорт и пустая обёртка

`import heapq` (строка 25) не используется ни разу, а `frontier_sa`
(строки 172-175) только реэкспортирует `weakest_link_frontier_sa` через
локальный импорт. Мелочь, но вводит в заблуждение: неиспользуемый `heapq` —
след того самого потокового k-путного слияния, которого в `merge_all` нет
(находка 4), и читатель по импорту решит, что слияние потоковое.

### 15. Докстринги расходятся с кодом

- Строка 98: «Возвращает (nodes, first_occ)» — на деле строка 169 возвращает
  `nodes, first_occ, N`, и `main()` (строка 203) распаковывает три значения.
- Строка 6: «каждая запись 16 Б (key u64, pos u32, label u8)» — замеренный
  `itemsize` структурного dtype равен **13**: NumPy пакует поля без выравнивания.
  Все оценки диска и памяти из докстринга завышены на 23 %, а невыровненный шаг
  в 13 байт — сам по себе причина того, что представление `keys` неконтинуально.
