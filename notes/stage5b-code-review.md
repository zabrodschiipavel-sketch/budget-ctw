### Находка 16 (обнаружена при внедрении fallback, 2026-08-05)

`np.searchsorted` по полю structured-массива (`blk["key"]`, шаг 17 байт) — массив
non-contiguous, и numpy делает ПОЛНУЮ КОПИЮ O(n) при каждом вызове: замерено
**15965 мкс против 2.4 мкс** на contiguous-копии. На 127K узлов это 2000+ секунд
вместо 1.6 с. Классический скрытый блокер: на малых тестах (всё в кэше, копия
33.6 МБ успевает) расхождение не видно, на полном корпусе — сутки.
Исправление: `np.array(blk["key"], copy=True)` и т.д. — один раз на блок (4M записей
= 33.6 МБ × 3 поля, пик ~170 МБ на блок, последовательно).

## Архитектурные изменения

### `sa_prod.py` — полная переработка
1. **Генерация**: векторно, чанки `CHUNK` (env `SA_CHUNK`), dtype `u64/u64/u8` (17 B упаковано).
2. **Слияние**: `MERGE_WAY` (env `SA_MERGE_WAY`, default 8) потоковое k-way через `heapq.merge`-подобный `BlockReader` + `open_memmap` выход. Никакого `concatenate` всего датасета. Пик памяти ~2 блока × `MERGE_BLOCK` (env, default 1M).
3. **Дерево**: `TreeArrays` — 6 параллельных `list[int]` + `first_occ`, никаких Python-объектов на узел. Строится рекурсией с `searchsorted(keys, np.uint64(T))`.
4. **Frontier**: `weakest_link_arrays` — то же, что Rust `weakest_link`: `cap=8M`, перестройка, `(α, first_occ, dep, u)` в куче, O(n) память.
5. **Чистка**: `created: list[Path]` — только файлы текущего запуска; `pref.memmap` закрыт явно; временная папка сохраняется если `--keep` или если пользователь передал существующий `--tmp`.
6. **Edge cases**: пустой вход — ошибка; кириллица в stdout работает под `reconfigure`; D > 53 валиден; D до 63.

### `comparator_sa_ref.py` — минимальные правки

- heap entry = `(α, first_occ, dep, u)`;
- добавлен heap cap (8M) + перестройка (как в Rust);

### `sa_prod_fast.py` — блочный build (fallback, 2026-08-05)

После code review выяснилось, что исходный build по memmap-файлу 13.6 ГБ с
`searchsorted` на каждый узел thrash-ит при свободной RAM 0.3 ГБ (20+ часов и
без конца). `sa_prod_fast.build_tree_fast`:
- большие диапазоны (> RAM_BLOCK=4M) — ручной бинарный поиск по memmap,
  локализованный в [lo, hi); таких узлов ~500 (верхние ~9 уровней);
- диапазоны ≤ 4M — блок читается в RAM (`np.array(mm[lo:hi])`), под-дерево
  строится по contiguous-копиям полей (searchsorted 2.4 мкс, не 16 мс);
- BFS по уровням, узлы создаются `emit`-ом сразу со счётчиками и передаются
  в следующий уровень (важно: не создавать «заглушки» и отдельные узлы для
  того же диапазона — теряются счётчики, см. баг с n=[0,0]);
- first_occ внутренних mem-узлов = min по детям (пост-обработка уровня).
- верификация: 512 КБ D=48 — 126 863 узла за 1.6 с, полное дерево
  **бит-в-бит с Rust explicit** (63 432 листа, 1 638 147.758 бит), frontier
  29 621 точка; 2 МБ D=48 — 320 239 узлов за 4.3 с, полное дерево бит-в-бит
  (160 120 листьев, 6 140 846.502 бит).
- бюджетные ответы: расхождения только при почти равных α (float-шум разных
  libm: MSVC vs Python), ≤ 11 бит на 6.14M (1.8e-6 относительных) на 2 МБ.

## Статус полного D=48 / 100 MB

Полный прогон запускается так:

```bash
python tools/sa_prod.py data/enwik8 --depth 48 \
    --budgets 1000,10000,56000,100000,466021,500000,857401 --points 3
```

Ожидаемые ресурсы (с `CHUNK=8M`, `MERGE_WAY=8`):
- **диск**: ~2× исходник = 200 МБ чанков + 200 МБ слияний ≈ **400 МБ** пика в `.sa_tmp`
- **RAM**: 2 блока × 1M × 17 B ≈ **34 МБ** + префиксные суммы memmap (800M × 8 B = 6.4 ГБ на диске) + дерево 2–5M узлов × ~40 B ≈ **100–200 МБ** + frontier куча cap 8M × 48 B ≈ **400 МБ**. Итого **< 1 ГБ RSS**.
- **время**: генерация ~3 мин, слияние ~5 мин, дерево ~3 мин, frontier ~3 мин → **~15 мин** без page file.

Предыдущий запуск (с `concatenate` + `searchsorted` float64 + без cap) съел 20+ ГБ и не финишировал. Переписанная версия должна уложиться в память машины и отдать итоговую таблицу сожаления для D=48 на полном корпусе — **финальный ответ на вопрос П4**.
