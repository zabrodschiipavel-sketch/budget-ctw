# Этап 8 — план формализации доказательства в Lean 4

План от 2026-08-14. Контекст: пункты (2) и (3) П4 сейчас не доказаны даже на
бумаге ([gap-to-100.md](gap-to-100.md)), поэтому это план **параллельного
трека**, а не «переписать готовое в Lean».

## 0. Зачем вообще Lean в этой задаче

Премия его не требует: правила фонда просят препринт + код. Тем не менее два
аргумента конкретно для П4:

1. **Репозиторий уже один раз потерял месяцы на семантике определения, а не на
   доказательстве.** Компаратор минимизировал по строгому подклассу T_M
   (обрыв на первом унарном узле) — ошибка жила в пяти реализациях сразу и
   ловилась только сравнением с самой собой ([аудит](stage5b-comparator-audit.md)).
   Определение `T_M` в Lean — это ровно то место, где такая ошибка становится
   невыразимой: класс задаётся один раз, и все утверждения квантифицируются по
   нему.
2. **Приёмка — комиссия с 30-дневной рецензией и правом внешнего рецензента.**
   Машинно проверенная цепочка «KT → смесевое неравенство CTW → разложение
   сожаления» переводит спор о пункте (2) из «верю/не верю оценке» в
   «проверьте `lake build`».

Чего Lean **не** даёт: он не найдёт доказательство. Сначала бумага, потом
формализация — иначе трек превращается в самоцель (главный риск, см. §6).

## 1. Инфраструктура

```
formal/
  lakefile.toml          — зависимость: mathlib4
  lean-toolchain         — прибитая версия
  BudgetCTW/*.lean       — модули §3
  blueprint/             — leanblueprint: LaTeX ↔ Lean, граф зависимостей
```

Решения, фиксируемые до первой строки (тот же принцип, что в `design-spec`:
развилки выбираются один раз):

- **Всё конечно.** Последовательность — `x : Fin T → Bool`, контекст —
  `List Bool` (последние биты, ближний первым). Никакой теории меры: она
  понадобится максимум в нижней границе, и то не обязательно.
- **Считаем вероятности, а не логарифмы.** Все леммы — мультипликативные
  неравенства на `ℝ` с гипотезами положительности; `L p := -Real.logb 2 p`
  вводится один раз наверху и переносит неравенства монотонностью
  (`Real.logb_le_logb`). Суммы логарифмов в промежуточных леммах — главный
  источник боли в Lean, произведения — нет.
- **Два компаратора с самого начала.** `L_H` (эмпирическая энтропия, то что
  меряет код) и `L_KT` (то, что стоит в постановке). Определение обоих в Lean
  и лемма связи между ними закрывает дыру №2 из [gap-to-100.md](gap-to-100.md)
  на уровне определения, а не сноски.
- Из Mathlib используем `Real.logb`, `Real.negMulLog`, `Real.Gamma`,
  `Nat.factorial`, `Finset.prod_le_prod`, `Finset.sum_le_sum`, Stirling из
  `Mathlib.Analysis.SpecialFunctions.Stirling`, для нижней границы —
  `Fintype.card` и энтропийный API (из вклада PFR). **Точные имена сверить с
  текущим Mathlib при старте** — они мигрируют.

## 2. Порядок разработки: сверху вниз через `sorry`

Первый коммит трека — `BudgetCTW/Statements.lean`, который компилируется,
содержит все определения и все итоговые теоремы с `sorry`. Это «контракт»:
его можно ревьюить, класть в приложение препринта и по нему видеть, что
именно осталось доказать. Дальше `sorry` вычёркиваются снизу вверх.

## 3. Модули и ключевые утверждения

Ниже — скелеты сигнатур (синтаксис проверяется при первой сборке, имена
Mathlib — тоже).

### `Basic.lean` — алфавит, последовательности, кодовая длина
```lean
abbrev Sym := Bool
abbrev Seq (T : ℕ) := Fin T → Sym
noncomputable def L (p : ℝ) : ℝ := -Real.logb 2 p
lemma L_antitone {p q : ℝ} (hp : 0 < p) (h : p ≤ q) : L q ≤ L p
```

### `Tree.lean` — класс сравнения T_M (главный страховочный модуль)
```lean
inductive CTree where
  | leaf : CTree
  | node : CTree → CTree → CTree

def CTree.leaves : CTree → ℕ
def CTree.depth  : CTree → ℕ
def CTree.leafOf : CTree → List Bool → List Bool   -- в какой лист падает контекст

def TM (D M : ℕ) : Set CTree := {S | S.depth ≤ D ∧ S.leaves ≤ M}
```
Здесь же — **сертификат аудита**, лемма, которую стоит доказать первой, потому
что она дешёвая и закрывает уже случившуюся ошибку:
```lean
def contracted (S : CTree) : CTree            -- обрыв на первом унарном узле
theorem contracted_mem_TM   : contracted S ∈ TM D M → S ∈ TM D M → True  -- подкласс
theorem min_TM_le_min_contracted (x : Seq T) :
    minCost (TM D M) x ≤ minCost (contractedClass D M) x
```
То есть: старый класс — строгий подкласс честного, минимум по честному не
больше. Ровно это утверждение аудит проверял численно.

### `Counts.lean` — счётчики
`counts : Seq T → List Bool → ℕ × ℕ` и аддитивность по детям
(`counts u = counts (0::u) + counts (1::u)`) — техническая, но нужна везде.

### `KT.lean` — оценщик Кричевского–Трофимова
```lean
noncomputable def kt : ℕ → ℕ → ℝ            -- ∏ (2i+1)/(2i+2) в правильном порядке
theorem kt_pos (a b : ℕ) : 0 < kt a b
theorem kt_succ_left  (a b : ℕ) : kt (a+1) b = kt a b * (2*a+1) / (2*(a+b)+2)
theorem kt_redundancy (a b : ℕ) :
    L (kt a b) ≤ (a+b) * H₂ (a/(a+b)) + (1/2) * Real.logb 2 (a+b+1) + 1
```
`kt_redundancy` — единственная тяжёлая аналитическая лемма всего трека.
Три пути, выбирать по бюджету времени:
- (а) через Γ-представление KT и явные двусторонние оценки факториала —
  честно, дорого (Stirling в Mathlib асимптотический, явные границы придётся
  доводить);
- (б) индукцией по n в духе оригинального доказательства Виллемса — дешевле,
  константа чуть хуже;
- (в) **параметризовать константу**: доказать `L (kt a b) ≤ nH + c₁ * logb 2 (n+1) + c₂`
  с абстрактными `c₁ c₂` и гипотезой существования, а конкретные значения
  подставить позже. Тогда провал (а)/(б) не блокирует ничего ниже по графу.
  Рекомендую сразу (в), а (а) закрывать в фоне.

### `CTW.lean` — смесевое неравенство (классика, лучший расход времени)
```lean
noncomputable def Pw (D : ℕ) (x : Seq T) : List Bool → ℝ   -- ½Pe + ½Pw₀Pw₁
theorem ctw_mixture (S : CTree) (hS : S.depth ≤ D) (x : Seq T) :
    2 ^ (-(Γ S : ℝ)) * ∏ u ∈ S.leafSet, kt (counts x u).1 (counts x u).2
      ≤ Pw D x []
```
Структурная индукция по дереву, чистая алгебра, никакого анализа — самая
Lean-дружелюбная часть. Отсюда сразу следует «CTW-компонента» границы:
`L_CTW ≤ Γ(S) + Σ_leaves L(kt …)` для любого S класса.

### `Algo.lean` — бюджетный алгоритм как система переходов
```lean
structure State (c M D : ℕ) where
  nodes    : Finset (List Bool)
  prefixClosed : ∀ u ∈ nodes, ∀ v, v <:+ u → v ∈ nodes
  card_le  : nodes.card ≤ c * M
  cnt      : List Bool → ℕ × ℕ
def step  : State c M D → Sym → State c M D × ℝ      -- новое состояние и P(бит)
def L_A   (x : Seq T) : ℝ
theorem prob_sums_to_one (s : State c M D) : predict s 0 + predict s 1 = 1
```
`prob_sums_to_one` — тот самый инвариант, нарушение которого на этапе 4
выглядело как *улучшение* метрики (0.204 bpc). Формализовать его дёшево, а
цена ошибки уже измерена.

### `Eviction.lean` + `Decomp.lean` — предмет пункта (2)
```lean
theorem deferred_split_cost … :
    L (Pw_leafPhase …) - L (Pw_split …) = L (Pe_phase …)      -- замкнутая форма этапа 4
theorem budget_regret (x : Seq T) :
    L_A x - minCost (TM D M) x
      ≤ Γ_max M + (M/2) * Real.logb 2 T + E_T x + ε * D * T
```
Блокируется бумажным доказательством (2b)/(2c) — до него в Lean кладётся
только формулировка.

### `Rounding.lean` — Q24 и таблицы
Абстрактная модель: операция = точное значение ± ε. Накопление ≤ ε·D·T —
индукция по символам. Бонус, который стоит взять: **LUT конечна**, поэтому
её оценку ошибки можно проверить исчерпывающе через `native_decide` по всем
записям таблицы, а не постулировать. Это дешёвый пункт с высокой
убедительностью для рецензента.

### `Lower.lean` — пункт (3)
Формализуется **только формулировка**, пока не выбрана форма A/B/опровержение
(см. [gap-to-100.md §3](gap-to-100.md)):
```lean
structure MemPredictor (S : ℕ) where
  St : Type
  fin : Fintype St
  card_le : Fintype.card St ≤ 2 ^ S
  pred : St → List Bool → ℝ
  next : St → Sym → St
theorem lower_bound … : ∃ x : Seq T, L_A x - minCost (TM D M) x ≥ c * T
```

## 4. Вехи и оценка

| Веха | Содержание | Оценка | Блокирует |
|---|---|---|---|
| M0 | скелет + `Basic` + `Tree` + `Statements.lean` со всеми `sorry` | 2–3 дня | ничего |
| M1 | `Counts`, компараторы `L_H`/`L_KT`, **сертификат аудита** | ~1 неделя | ничего |
| M2 | `KT.kt_redundancy` (путь «в») | 3–5 дней | путь (а) — фон, 2–4 недели |
| M3 | `CTW.ctw_mixture` | 1–2 недели | — |
| M4 | `Algo` + инвариант Σ=1 + `Decomp` | 2–4 недели | бумажное (2b) |
| M5 | `Rounding` + `native_decide` по LUT | ~1 неделя | — |
| M6 | `Lower` | открыто | бумажное (3) |

M0–M3 (≈3–4 недели) дают самостоятельный результат: машинно проверенная
классическая часть границы (структурная + параметрическая цена) и
формализованный класс сравнения. Это можно печатать приложением к препринту
даже если (2) ещё не доказан.

Полная формализация всех шести вех — 8–14 недель, то есть больше, чем весь
бюджет задачи по оценке фонда (~5 недель специалиста). **Поэтому план
намеренно останавливается на M0–M3 + M5 как на обязательной части**, а M4
делается только если бумажное доказательство (2) устоялось, M6 — скорее всего
остаётся на бумаге: там содержание в конструкции, а не в выкладке, и цена
формализации максимальна при минимальной пользе.

## 5. Связь с препринтом

Вести через `leanblueprint`: каждая теорема бумаги получает Lean-имя, граф
зависимостей генерируется автоматически. Побочный, но важный эффект — граф
показывает *дыры* до того, как они попадут в абстракт: ровно та проверка,
которой не хватило `stage7-preprint.tex`, где в абстракте оказались теоремы,
которых нет.

## 6. Риски

- **Lean съедает проект.** Признак: неделя без продвижения по бумажной части
  (2). Реакция — заморозить трек на достигнутой вехе; M0–M3 самодостаточны.
- **Формализуется не то.** Единственная защита — сначала бумажный текст
  леммы, потом её Lean-имя. Формулировка, придуманная сразу в Lean, обычно
  оказывается удобной для доказательства и бесполезной для препринта.
- **Делегирование free-моделям здесь не работает.** Lean они генерируют
  правдоподобно и некомпилируемо, а проверка стоит дороже написания.
  Делегировать имеет смысл только LaTeX-прозу блюпринта и перевод уже
  доказанных на бумаге лемм — с обязательной локальной сборкой до приёмки
  результата.
