Компаратор `src/comparator.rs` работает и проверен (Rust ≡ Python-эталон, включая

## SA-бэкенд: решение найдено

Ключевые результаты отладки (2026-08-04):

1. **Контракция — не Patricia**: узел с ≤1 ребёнком становится листом НАВЕРХУ
   унарной цепочки (поглощает счётчики всего поддерева), а не сжимается в ребро.
   Прежний `find_first_split` спускался сквозь унарные участки — отсюда все
   расхождения.

2. **Тай-брейк при равных α**: explicit-дерево нумерует узлы в порядке создания
   = (позиция первого вхождения контекста в потоке, глубина) лексикографически
   (проверено: 0 расхождений из 8243 узлов). SA-бэкенд использует heap-ключ
   (α, first_occ, dep) — последовательность отщипываний ИДЕНТИЧНА explicit.

3. Проверки: 15/15 фиксированных кейсов + 40/40 рандомизированных — полное
   совпадение последовательностей точек (не только бюджетных ответов).

## SA на полном enwik8 D=48 — ВЫПОЛНЕН (2026-08-05)

Раньше казалось, что SA не влезет: 800M записей, ключи u64 — 6.4 ГБ + SA-массив
6.4 ГБ > 12 ГБ при ~0.5 ГБ свободной памяти. Решение — внешняя сортировка
(`sa_prod.py`: чанки по 8M записей → k-way слияние на диск) + блочный build
(`sa_prod_fast.py`): контрактированное дерево 4.4M узлов влезает (~1 ГБ).
Полный цикл 2 ч 25 мин. Результаты — в stage5b-comparator-results.md.

## Отклонённые «ускорения»

- Не разворачивать узел при n_u == 1 во время online-построения — некорректно
  (узел может получить второе вхождение позже; меняет число узлов).
- SA-дерево «только с бинарными детьми» без явного моделирования unary-путей —
  давало другую frontier на unary-корпусах (счётчики накапливаются не там).
- Строгое сравнение точек без учёта тай-брейка — «ложные» расхождения на
  α=0-плато (коллинеарные точки с равной стоимостью); бюджетные ответы
  совпадали, но последовательности нет — исправлено тай-брейком (α, first_occ, dep).

## Полный D=48/100MB — fast build (2026-08-05) — ЗАВЕРШЁН

Старый build по memmap 13.6 ГБ с searchsorted на каждый узел thrash-ил
(20+ ч, 0.3 ГБ свободной RAM). Заменён на tools/sa_prod_fast.build_tree_fast:

- верхние ~9 уровней (диапазоны > 4M записей): ручной бинарный поиск по
  memmap, ~500 узлов;
- ниже: блок 4M записей копируется в RAM, под-дерево строится по
  contiguous-копиям полей (searchsorted 2.4 мкс, а не 16 мс по stride-view);
- BFS по уровням; узлы создаются emit-ом сразу со счётчиками.

Верификация: 512KB D=48 — 126 863 узла за 1.6 с, полное дерево бит-в-бит
с Rust explicit (63 432 листа, 1 638 147.758 бит); 2MB D=48 — 320 239 узлов
за 4.3 с, полное бит-в-бит (160 120 листьев, 6 140 846.502 бит).
Бюджетные ответы vs Rust: расхождения ≤ 11 бит на 6.14M (1.8e-6) — только
float-шум порядка отщипываний при почти равных alpha (MSVC vs libm).

**Итог прогона (2026-08-05, 2 ч 25 мин)**: 800M записей, дерево 4 417 447
узлов (2 208 723 внутренних), 2 208 724 листа, полное 281 180 922.052 бит
= 2.8118 бит/байт. Frontier 970 702 точки за 2.1 мин. Бюджетная таблица —
в notes/stage5b-comparator-results.md. Перекрёстная проверка: M=1000
совпадает с Rust explicit D=24 до бита (450 382 838).

Страховка: `tools/sa_build_only.py <merged.npy> --depth 48 --budgets ...` —
пересобирает дерево и frontier из готового отсортированного файла без
генерации/слияния (вход не удаляется). Проверен на 2KB D=8: даёт бит-в-бит
тот же результат, что run_sa_full (9469.098 бит, бюджеты 15840.626/12538.667).

Ограничение прогона: frontier не сохранялся на диск (только напечатанные
бюджеты), merged-файл удалён. Для новых бюджетов — повторный прогон с --keep.
